# 对象存储（S3）操作手册

本分支（`local-spacebackend`）是 **Postgres + 本地盘**：上传字节落 `data/uploads/`，知识读
`knowledge/`，派生 Parquet 落 `.cache/xlsx/`。对象存储只剩一个用途——
**手动把知识目录推一份到 S3 做备份/分发**（`scripts/okf_push_s3.py`）。

> 想看"上传与读路径都走对象存储"的那一版，见分支 `mirage-s3`（ADR-0018）。

## 1. 起对象存储（可选）

仓库根有 `compose.yaml`（Redis + SeaweedFS，Postgres 被注释掉），一键起：

```bash
MSYS_NO_PATHCONV=1 docker compose up -d
```

端口可用 `REDIS_PORT` / `SEAWEEDFS_S3_PORT` / `SEAWEEDFS_MASTER_PORT` / `SEAWEEDFS_FILER_UI_PORT` 覆盖，
默认 S3 网关在 `http://127.0.0.1:8333`。不用 compose 也可以直接 `docker run`，参数见 compose 里的注释。

## 2. 配置

`config.yaml`：

| YAML 键 | 默认 | 说明 |
|---|---|---|
| `s3.endpoint` | 空（空 = 未启用） | 网关地址，如 `http://127.0.0.1:8333` |
| `s3.bucket` | `aegra-blobs` | 桶名，`okf_push_s3.py` 会按需创建 |
| `s3.region` | `us-east-1` | 填什么都行（SeaweedFS 不校验） |

`.env`（只有凭证）：

| 变量 | 默认 | 作用 |
|---|---|---|
| `S3_ACCESS_KEY` / `S3_SECRET_KEY` | `dev` / `dev` | 凭证（SeaweedFS 未配 IAM 时任意值） |

> boto3 必须用 path-style：给了 `endpoint_url` 之后它仍默认 virtual-host，`aegra-blobs.127.0.0.1:8333`
> 解析不了。`shared/session/blobs.py` 已写死 `Config(s3={"addressing_style": "path"})`，
> 自己写脚本时别忘。

## 3. 推知识到 S3

```bash
PYTHONPATH=. .venv/Scripts/python.exe scripts/okf_push_s3.py --dry-run   # 只列出要传什么
PYTHONPATH=. .venv/Scripts/python.exe scripts/okf_push_s3.py             # 真传
```

- 前缀是 `okf/<space>/…`，与本地 `knowledge/<space>/…` 一一对应；`s3.endpoint` 为空时脚本直接报错。
- 推完不影响本机运行：服务进程从不读 S3。
- 想校验：`aws --endpoint-url http://127.0.0.1:8333 s3 ls s3://aegra-blobs/okf/ --recursive`，
  或 `PYTHONPATH=. python -c "from shared.session import blobs; print(blobs.client().list_objects_v2(Bucket=blobs.bucket(), Prefix='okf/')['KeyCount'])"`。

## 4. 排错

| 现象 | 原因 |
|---|---|
| 脚本报 `没有配置对象存储` | `config.yaml` 的 `s3.endpoint` 为空，或被 `S3_ENDPOINT=""` 覆盖 |
| `AccessDenied` | `.env` 里 `S3_ACCESS_KEY`/`S3_SECRET_KEY` 与实际网关不一致（SeaweedFS 未配 IAM 时任意值都能过） |
| `Connection refused` | 网关没起；compose 的 8333 端口被别的容器占用时用 `SEAWEEDFS_S3_PORT` 换端口 |
| 桶已存在但脚本报 403 | 别的进程用另一个 access key 建的桶；SeaweedFS 未配 IAM 时换回建桶时的 key，或换桶名 |

## 5. 清理

`okf/` 下的对象是知识目录的副本，本地 `knowledge/` 才是真相：

- 删对象后不影响服务（本分支不读它），下次 `okf_push_s3.py` 会重建。
- 若曾在这台机器上跑过 `mirage-s3` 分支，桶里可能还留着 `uploads/<owner>/<thread>/…` 与
  `xlsx-derived/…`。这些在本分支没人读，可直接
  `aws --endpoint-url … s3 rm s3://aegra-blobs/uploads/ --recursive`（删前确认没在跑旧分支）。
